# Internationalization (i18n)

**Estado (sesión 19, 29 jul 2026):** andamiaje conectado con `next-intl`.
Inglés por defecto + español. El switcher está en el sidebar. **Un** módulo de
la capa de análisis (`draft-odds.ts`) está migrado como patrón de referencia;
faltan 12 (ver abajo).

## Decisiones

- **Cookie-based, sin routing de URL.** El locale vive en la cookie
  `NEXT_LOCALE`; las URLs no cambian (`/event/MXTOL` sigue igual). No hay
  middleware de rutas ni `<Link>` que reescribir, y no rompe deep-links, URLs
  compartidas ni la PWA. Detección: cookie → `Accept-Language` → default `en`.
- **Herramienta:** `next-intl` v4 en modo *without i18n routing*.

## Piezas

| Archivo | Rol |
|---|---|
| `i18n/config.ts` | `locales`, `defaultLocale`, `LOCALE_COOKIE`, `isLocale` (módulo plano) |
| `i18n/locale.ts` | Server actions `getUserLocale` / `setUserLocale` (leen/escriben la cookie) |
| `i18n/request.ts` | `getRequestConfig` de next-intl: resuelve locale + carga `messages/{locale}.json` |
| `next.config.ts` | `createNextIntlPlugin("./i18n/request.ts")` envuelve el config base |
| `app/layout.tsx` | `<html lang={locale}>` + `<NextIntlClientProvider>` (hereda mensajes del request config) |
| `components/LocaleSwitcher.tsx` | Toggle en el sidebar; escribe la cookie vía server action + `router.refresh()` |
| `messages/en.json`, `messages/es.json` | Catálogos por namespace |

## Traducir un componente

```tsx
import { useTranslations } from "next-intl";        // client
// import { getTranslations } from "next-intl/server"; // server components

function MyComponent() {
    const t = useTranslations("MyNamespace");
    return <p>{t("greeting", { name })}</p>;
}
```

Mensaje ICU: `"greeting": "Hola {name}"`.

## El patrón que importa: la capa de análisis NO devuelve prosa

**Esta es la parte que se subestima.** ~13 módulos de `lib/` generan texto en
español *dentro del análisis* (no en componentes). Si i18n se trata como
"traducir componentes", el Oracle sigue hablando español desde el motor.

**Regla:** una función de análisis que hoy devuelve una frase debe devolver una
**clave de traducción + sus parámetros**, y el componente la renderiza con
`next-intl`. La lógica no elige idioma.

### Ejemplo de referencia — `lib/draft-odds.ts`

Antes:
```ts
basis: `Seed ${seed} da ${(base*100).toFixed(0)}%, pero estar en el percentil ${oprPct}...`
```
Después:
```ts
export type DraftBasis =
  | { key: "captain"; seed: number; alliances: number }
  | { key: "seedRate"; seed: number }
  | { key: "oprUp"; seed: number; basePct: number; oprPct: number }
  | { key: "oprDown"; seed: number; basePct: number; oprPct: number };
// draftOdds(...).basis = { key: "oprUp", seed, basePct, oprPct }
```
El consumidor (`ConsistencyTracker.tsx`):
```tsx
const tOdds = useTranslations("DraftOdds");
const basisText = (b: DraftBasis) => { const { key, ...params } = b; return tOdds(key, params); };
```
Y el redondeo (`toFixed(0)`) se hace en el análisis (params ya redondeados), no
en el mensaje — el catálogo solo interpola.

## Regla activa: ningún string nuevo hardcodeado

Desde ahora, cualquier archivo que se toque extrae sus strings a un namespace.
No se escriben frases nuevas en español (ni inglés) inline en componentes ni en
`lib/`.

Para cada uno: cambiar el retorno a clave+params, añadir el namespace a
`messages/{en,es}.json`, cablear el/los consumidor(es), y un test de que devuelve
la estructura (no una cadena) como en `draft-odds.test.ts`.

Además, el grueso de **strings de UI en componentes** (labels de nav, botones,
formularios) sigue hardcodeado — extracción incremental al tocar cada archivo.
